# AvaloniaAuth

Кроссплатформенное настольное приложение на **C#**, **.NET 10** и **Avalonia UI**, демонстрирующее реализацию сценариев авторизации и регистрации, архитектуру MVVM, внедрение зависимостей и асинхронное взаимодействие с HTTP API.

Приложение содержит интерфейс входа и регистрации, позволяет получать данные авторизованного пользователя и завершать сеанс. Для разработки предусмотрена возможность переключения между удалённым API и эмулятором HTTP-ответов.

## Возможности

- **Авторизация** по адресу электронной почты и паролю.
- **Регистрация пользователя** через отдельный диалог.
- **Управление состоянием авторизации**: получение профиля пользователя и выход из аккаунта.
- **MVVM** — разделение представлений, моделей представления и сервисов.
- **Внедрение зависимостей (DI)** с помощью `Microsoft.Extensions.DependencyInjection`.
- **HTTP-взаимодействие** через `HttpClient`.
- **Эмуляция HTTP API** для разработки и проверки сценариев без зависимости от доступности удалённого сервера.
- **Проверка пользовательского ввода**, включая обязательные поля, формат email и длину пароля.
- **Асинхронные операции** при выполнении запросов к API.
- **Обмен сообщениями между ViewModel** с использованием CommunityToolkit.Mvvm.
- **Оформление Fluent UI** с использованием темы Avalonia Fluent и шрифта Inter.

## Архитектура

Проект использует паттерн **MVVM** и разделяет интерфейс, логику представления, прикладные сервисы и работу с данными.

```text
Application
├── Views/        # Представления Avalonia UI
├── ViewModels/   # Состояние интерфейса и команды
├── Services/     # Авторизация, работа с данными и диалогами
├── Data/         # Доступ к данным и HTTP API
├── Dto/          # Объекты передачи данных
├── Models/       # Модели приложения и пользователя
├── Messages/     # Сообщения для обмена состоянием
├── Helpers/      # Вспомогательные классы
└── Test/         # Эмуляция HTTP-ответов (не отдельный тестовый проект)
```

### Сценарий авторизации

1. Пользователь вводит email и пароль.
2. `LoginViewModel` проверяет введённые данные.
3. `AuthService` инициирует запрос через слой доступа к данным.
4. Приложение получает токены авторизации.
5. Затем запрашивается профиль текущего пользователя.
6. Состояние авторизации обновляется, и интерфейс переключается на авторизованную часть приложения.
7. При выходе отправляется запрос на завершение сеанса, после чего состояние авторизации очищается в памяти приложения.

Регистрация запускается из интерфейса входа и выполняется через отдельный диалог.

## Источник данных и режим эмуляции

Приложение можно настроить для работы с удалённым API или локальным обработчиком, который эмулирует HTTP-ответы.

Переключатель находится в `App.axaml.cs`:

```csharp
const bool UseFakeHandler = false;
```

### Удалённый API

При значении `false` запросы отправляются на:

`https://fakeapifordevs.vercel.app`

Доступность и поведение удалённого сервиса зависят от внешнего API.

### Режим эмуляции

Установите `UseFakeHandler` в `true`, чтобы направлять запросы в `FakeHttpMessageHandler`, расположенный в папке `Test/`.

Эмулятор предусматривает ответы для следующих маршрутов:

| Метод | Маршрут | Назначение |
|---|---|---|
| `POST` | `/api/auth/register` | Регистрация пользователя |
| `POST` | `/api/auth/login` | Авторизация |
| `GET` | `/api/auth/me` | Получение профиля текущего пользователя |
| `POST` | `/api/auth/logout` | Выход из аккаунта |

Эмулятор можно дорабатывать для моделирования различных ответов сервера и задержек при обработке запросов. Это позволяет демонстрировать пользовательские сценарии без необходимости обращаться к реальному API.

> **Примечание:** папка `Test/` не является отдельным тестовым проектом. Сейчас в ней размещён класс эмуляции HTTP-взаимодействия. Создание полноценного тестового проекта запланировано на будущее.

## Принципы реализации

В проекте демонстрируются следующие подходы:

- разделение ответственности с помощью MVVM;
- внедрение зависимостей через конструкторы;
- централизованная регистрация сервисов приложения;
- использование наблюдаемых свойств и команд CommunityToolkit.Mvvm;
- обмен сообщениями между моделями представления;
- валидация пользовательского ввода;
- асинхронное выполнение HTTP-запросов;
- отделение логики авторизации от низкоуровневого HTTP-взаимодействия;
- эмуляция ответов API без необходимости менять код сервиса авторизации.

## Ограничения и безопасность

Проект предназначен прежде всего для демонстрации архитектуры настольного приложения и сценариев авторизации. Его не следует считать готовым production-решением для аутентификации.

- Эмулятор возвращает заранее заданные ответы и не заменяет серверную проверку учётных данных.
- Работа с удалённым API зависит от доступности стороннего сервиса.
- Токены авторизации хранятся в памяти приложения; постоянное защищённое хранилище токенов не реализовано в текущем сервисе авторизации.
- Для production-приложения следует предусмотреть безопасное хранение токенов, обработку ошибок, корректную проверку сертификатов TLS и валидацию данных на стороне сервера.
- Тестовые ответы и токены эмулятора нельзя использовать как реальные секреты авторизации.
